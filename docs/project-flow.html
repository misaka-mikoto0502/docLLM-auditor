二、各阶段拆解

① 文档解析 —— PDF 文本 → API 单元

环节实现说明
文本提取pdf_lib.extract_pages_clean PyMuPDF 取文本层；按坐标带裁掉页眉（<9% 页高）与页脚（>90% 页高）
表格重建_table_lines / _cell_text find_tables() 取结构，word 级 bbox 精确裁单元格，按 y 聚类成行，输出行首带 | 的管道行（防误命中分段正则）
缓存pages_clean.json 落 audit/work/m5/<产品>/，ModelArts 特例放 audit/work/ 顶层；已存在则秒回，--force 重解析
条目切分segment.segment_apis 以「API 标题（N.N 中文 - English）」为条目起点，缓冲功能介绍/授权信息等前导，遇 URI 标签 + METHOD path 正式开单元；支持折行 URI 合并与兜底标题回溯
产物units.json + m5_report.md 单元字段：chapter / no / title_cn / api_en / method / path / start_page / text

② 任务矩阵 —— 条目 × 规则类别

环节实现说明
规则装载pdf_lib.load_rules读 spec_rules.json → by_no 索引（规则号 → 完整规则，含 text / blocks / keywords）
废弃剔除deprec.partition_units保守口径：仅当 title / path 命中「废弃 / 弃用 / deprecated / 已下线」才排除，正文命中不算（宁可少排除）
规则解析cmmatch.resolve_rules配置里写前缀（如 ARG-010），运行时按前缀匹配真实规则号（ARG-010-01-2507-2507-M），兼容多后缀版式
任务枚举build_tasksunit 模式：每条目 × 6 个类别；doc 模式：整篇 1 个任务（DOC-010/020/030）
试运行--dry-run只枚举任务、校验规则解析与 prompt 长度，不调 LLM、不改产物

③ LLM 裁决 —— 单条目 × 单类别 → per_rule 判定

提示词骨架（固定装配顺序）
TASK → IRON_RULES（4 条铁律 + 5 步判别）→ EXAMPLES（甲/乙/丙 占位示例）→ 输入 → 规则卡 → 输出契约。关键指令放首尾，输入/规则夹中间，减小长文信息丢失。
规则卡只送原文
只送规则号 + 正文原文 + 规范示例，不送中文要点/checks（转述与原文非 100% 一致，喂模型会叠误差）。
长文本截断
_cap_text：首 35% + 各规则关键字命中窗口 ±400 字符 + 尾 15%，默认上限 28000 字符（可用 CMM_CAP 覆盖）。
grounding 校验
先整段去空白子串匹配；失败再 token 级（逗号/顿号/分号分隔的每片都必须命中）。confirmed 未落地 → 降 uncertain，防脑补证据。
并发与容错
ThreadPoolExecutor（默认 6-10 并发）；每任务完成即追加写 results.jsonl；连续失败达 --max-fail 熔断，保留已跑部分。
断点续跑
key = cat|method|path|start_page；只有 ok=True 且有 per_rule 才算完成，失败记录下次自动重试（避免数据空洞）。

④ 结果产出 —— 结构化结果 → 可筛选 Excel

产物内容
results.jsonl追加式原始记录，断点续跑的凭据
results.json全量重读 jsonl 后的完整记录数组
stats.json按类别 / 按规则的 confirmed-dismissed-uncertain 计数、去重违规（rule → 接口数）、任务成败
results.md人读报告：去重确认违规排行 + 逐条 confirmed 记录（含证据）
run_log.txt运行参数、续跑跳过量、耗时、熔断情况
llm_call_log.jsonl每次 LLM 调用的耗时 / prompt 长度 / 原始输出，供复盘
results.xlsx三表：判定明细（接口 × 规则 × 结果，带筛选冻结）、confirmed 违规（人工定案）、违规汇总（按规则聚合 + 印刷页码）

印刷页码由 _annotate_printed_pages 用 PyMuPDF 读页脚整行数字补上，best-effort，失败不中断主流程。

三、规则分档与判定范围

档位数量说明
A 档（执行）33 条 / 6 类 G1 请求 URI 与版本 · G2 动词·状态码·错误码 · G3 传输协议·编码·安全 · G4 请求/响应消息头 · G5 参数命名·通用词表·易用性 · G6 查询·分页·过滤·排序·时间
DOC（整篇级）3 条DOC-010/020/030 —— 单条目给不出证据，需整篇文档判定，demo 默认不执行
B 档（排除）4 条VER-030 / QUE-050 / BAS-060 / ASY-010（需跨接口聚合）
C 档（排除）18 条BAS/SLA/PUB/INT 等流程、性能、发布类规则
判定取向：不漏报 > 不错杀。同一违规常被多条规则冗余覆盖（如 STC-010 / STC-040），是刻意的召回设计；去重在 collect_stats 阶段按「规则 × 接口」完成。
33 这个数怎么来的（防记混）：A 档源全量 37 条 − DOC×3（整篇级，单条目给不出证据）− ASY-010（需跨接口聚合，归 B）= 33。实测 resolve_rules 对 6 个类别的 33 个前缀全部解析到真实规则，零缺失；其中 Mandatory 29 条、Optional 4 条（ARG-040 / ARG-050 / ARG-060 / FIL-010）。
已知陈旧注释：cm_demo_server.py:66 仍写「G1-G6, 34条」，与该文件第 3 行正文及配置实际值 33 不一致，是 2026-08-19 复核时漏改的。

四、两阶段设计：粗读 → 精修（设计意图 vs 便携包现状）

项目设计上确实是两步 LLM：阶段一粗读召回 → 阶段二精修裁定。但便携包里阶段一没有接线，主链路现在是单程全量精判。

设计意图（源码注释明确写了两阶段）

阶段实现职责
阶段一 · 粗读recall.run_recall
+ detect.detect_unit		 只缩小候选范围，不做判定。规则层（9 个客观探测器）出 high/medium/low 三档；LLM 层对每个接口召回「最可能违反的 top-k 语义规则号」，最多 8 条。客观项（URI 风格 / 版本号 / 计数命名 / query 驼峰）从 LLM 候选集排除，不重复判。
阶段二 · 精修cmmatch.adjudicate 法官式复核：一条目 × 一类别全部规则全文 → 逐条 confirmed / dismissed / uncertain，带逐字证据与 grounding 校验。
直接证据：recall.py:1「阶段一(初筛/召回)修正版」· recall.py:87「你是 API 文档合规审计的【粗略规则召回器】——只负责缩小候选范围，不做任何判定」· recall.py:95「不做裁判……判定的唯一权威是第二阶段」· detect.py:287「让 LLM 语义层召回、交由阶段二复核」。

现状：便携包里阶段一是死代码

检查项结果
detect 被哪些入口 import无。仅 recall.py:14 内部 import，而各入口只用到 recall.call_log()
run_recall 被谁调用无。只在 recall.py:217 定义，全仓库无调用点
主入口 cm_run_product.py 实际路径segment_apis → build_tasks（33 条全量）→ cmmatch.adjudicate，没有粗读过滤

所以便携包跑的是「一次精判打满」：每个条目 × 6 个类别 = 33 条规则全喂给 LLM，靠提示词铁律和 grounding 控制质量，而不是靠粗读先筛。README 里「auditlib 只带 7 个模块，剔除了 stage1 用到的 refine/report/resource_scope」也印证阶段一被裁掉了。

影响：算力上是「33 条全量」而非「top-8 候选」，成本明显更高；好处是不漏——粗读漏掉的规则精修阶段也捞不回来，全量判没有这个召回损失。若后续要接回阶段一，接线点在 cm_run_product.build_tasks，把 run_recall 产出的 llm_suspects / rule_candidates 作为类别过滤依据即可。
