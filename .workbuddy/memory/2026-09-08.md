## 项目熟悉 + 生成项目流程图

通读 portable 包源码（README、8 个脚本、auditlib 7 模块、spec 配置），产出 `docs/project-flow.html`（全景流程图 + 阶段拆解 + 规则分档 + 目录职责 + 运行顺序）。

### 项目本质
华为云 API 参考文档**合规审计**工具链：PDF → 清洗 → 切条目 → LLM 逐规则裁决 → Excel。

### 主链路（4 步）
1. `m5_parse_all.py` — PDF → pages_clean.json → units.json
   - `pdf_lib.extract_pages_clean`：坐标带裁页眉页脚（<9% / >90% 页高）+ `find_tables` 表格重建（word 级 bbox 裁单元格，输出行首带 `|`）
   - `segment.segment_apis`：API 标题（N.N 中文 - English）为条目起点，缓冲前导，遇 `URI` 标签 + METHOD path 开单元；支持折行 URI 合并、兜底标题回溯
2. `build_tasks` — deprec 剔废弃 → resolve_rules 前缀解析 → 条目 × G1-G6(33条) + DOC×3
3. `cmmatch.adjudicate` — build_prompt（TASK→铁律→示例→输入→规则卡→契约）→ 本地 vLLM → parse → grounded 校验
4. `collect_stats` / `render_md` → results.{json,jsonl,md} + stats.json → `gen_results_xlsx.py` 转三表 Excel

### 四种驱动入口（均复用主链路）
`run_all_products.py`（批量）/ `cm_demo_server.py`（Web 双路召回）/ `showcase_run.py`（票证演示）/ `agent_audit.py`（Agent 推理替代 vLLM）。

### 关键设计（易忘）
- **断点续跑**：key = `cat|method|path|start_page`；只有 `ok=True 且 per_rule 非空` 才算完成，失败记录下次重试（2026-08-13 教训：把 fail 当 done 会留数据空洞）。
- **熔断**：连续失败 ≥ `--max-fail` 提前终止，保留已跑部分。
- **grounding**：confirmed 证据必须逐字落地（整段子串 → token 级回退），否则降 uncertain。
- **提示词**：规则卡只送原文 + 规范示例，**不送** zh_summary/checks（转述叠误差）；示例用 甲/乙/丙 占位。
- **判定取向**：不漏报 > 不错杀，同一违规被多规则冗余覆盖是刻意设计，去重在 collect_stats 按「规则×接口」做。
- **长文本截断** `_cap_text`：首 35% + 关键字窗口 ±400 + 尾 15%，上限 28000（`CMM_CAP` 可覆盖）。
- LLM：`recall.py` 顶部 `LLM_BASE_URL`（本地 vLLM:8900），`ProxyHandler({})` 绕过 Windows 系统代理，密钥走 `LLM_KEY`。
- 规则分档：A 档执行 33 条/6 类；DOC×3 整篇级；B 档 4 条（含 ASY-010 需跨接口聚合）、C 档 18 条均排除。

用户提出两点质疑，逐一取证，**第一点用户记错，第二点用户部分正确、我原图有误**。

### Q1：A 类是不是 27 条？→ 否，确为 33 条
实测（跑 `resolve_rules` 对齐 spec_rules.json）：
- G1=6 / G2=5 / G3=5 / G4=5 / G5=6 / G6=6 → **合计 33，33 个前缀全部解析到真实规则，零缺失**
- 33 条中 Mandatory 29、Optional 4（ARG-040 / ARG-050 / ARG-060 / FIL-010）
- 来源公式（`gen_rule_A_doc.py:29-38`）：A_FULL 37 − DOC×3 − ASY-010 = 33，`assert len(A)==33`
- 全仓库 grep **无任何 "27"**（.agent_history 里的 "27" 是文件路径哈希片段，无关）
- `spec/A类规则整合_7类.md` 标题即为「33 条 · 6 类」，映射表求和 5+1+4+4+5+4+2+2+1+1+3+1=33
- 附带发现：`cm_demo_server.py:66` 注释仍写「34条」，与同文件第 3 行正文及配置值 33 冲突 → 2026-08-19 复核漏改的陈旧注释

### Q2：链路是不是「LLM 粗读 → LLM 精修」两步？→ 设计上是，便携包里没接线
- **设计意图确为两阶段**，有硬证据：`recall.py:1`「阶段一(初筛/召回)」、`recall.py:87`「粗略规则召回器…不做任何判定」、`recall.py:95`「判定的唯一权威是第二阶段」、`detect.py:287`「交由阶段二复核」、`recall.py:254-256` high/medium/low 三档分桶（medium → 阶段二复核）
- **但便携包内阶段一是死代码**：`detect` 无任何入口 import（仅 `recall.py:14` 内部引用）；`run_recall` 全仓库无调用点（只 `recall.py:217` 定义）；`cm_run_product` 直走 segment→build_tasks(33 条全量)→adjudicate，无粗读过滤。README「剔除了 stage1 用到的 refine/report/resource_scope」也印证。
- 结论：现在跑的是**一次精判打满**（条目×6 类=33 条全喂），靠铁律+grounding 控质量；代价算力高，收益是无粗读召回损失。
- 若接回阶段一：接线点在 `cm_run_product.build_tasks`，用 `run_recall` 的 `llm_suspects`/`rule_candidates` 做类别过滤。
